# Document editor UI market scan

**Date:** 2026-09-24  
**Purpose:** Inform a major editor-engine UI redesign. This is a scan of established document and writing products, official interaction guidance, and accessibility standards; it is not a claim to cover every editor on the market.

## Patterns across current editors

| Product | Officially documented interaction patterns | Useful takeaway |
|---|---|---|
| Google Docs | Persistent formatting toolbar plus matching Format menu; paragraph styles and search for fonts/colors; shortcut help opens with `⌘+/` or `Ctrl+/`. [Formatting](https://support.google.com/docs/answer/1663349?hl=en) · [Shortcuts](https://support.google.com/docs/answer/179738?hl=en) | Put frequent formatting in reach, but keep the same actions findable in menus and searchable help. Prefer named paragraph styles over one-off formatting. |
| Microsoft Word | Task-oriented ribbon groups, keyboard Key Tips, a command search field (`Alt+Q`), a collapsible ribbon, navigation and review panes. [Word shortcuts and ribbon navigation](https://support.microsoft.com/en-us/accessibility/word/keyboard-shortcuts-in-word) | Pair a dense, discoverable command surface with keyboard navigation and one global “find an action” route. Make secondary controls collapsible. |
| Apple Pages | Customizable toolbar, standard document menus, style shortcuts, page/layout controls, and table-of-contents navigation. [Pages guide](https://support.apple.com/guide/pages/welcome/mac) · [Toolbar customization](https://support.apple.com/guide/pages/customize-the-toolbar-tanafa2f718a/mac) | Make the primary strip user-relevant and keep platform conventions. Do not spend the toolbar on every available command. |
| LibreOffice Writer | Broad shortcut coverage, direct paragraph-style shortcuts, table navigation, and keyboard help. [Writer shortcut reference](https://help.libreoffice.org/latest/en-US/text/swriter/04/01020000.html) | Serious editing benefits from shortcuts for structure and navigation, beyond the usual bold/italic set. |
| ONLYOFFICE | Ribbon key tips, broad Windows/macOS shortcut tables, and user-customizable shortcut mappings. [Shortcuts](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/keyboardshortcuts.aspx) · [Advanced settings](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/AdvancedSettings.aspx) | Teach commands in place through visible key tips; let experienced users adapt bindings. |
| Zoho Writer | Shortcuts grouped by File, Edit, View, Insert, Format, tables, comments, and review; includes Focus Typing and Markdown shortcuts. [Shortcuts](https://help.zoho.com/portal/en/kb/writer/getting-started/overview/articles/shortcuts) · [Text tools](https://help.zoho.com/portal/en/kb/writer/editing-formatting/working-with-text/articles/working-with-text) | Organize actions in categories that match user tasks. Offer a low-distraction writing mode as an explicit view option. |
| Notion | Slash commands for in-context creation/formatting, Markdown shortcuts, and a short list of popular commands alongside full shortcut help. [Keyboard shortcuts](https://www.notion.com/help/keyboard-shortcuts) | Inline command discovery can aid newcomers and keyboard users when the editor is block-oriented. It should complement visible controls, not make basic operations depend on memorizing syntax. |
| Craft | Formatting is available from selection controls and `/style`; document-level styling is in a dedicated Style surface, while document styling supports fonts/colors/backgrounds. [Document styling](https://support.craft.do/hc/en-us/articles/10293992410780-Document-Styling) | Separate text-level formatting from page-level appearance; keep contextual formatting near the selection. |

These products converge on a stable model: document title and document actions above; a small set of frequent formatting controls; deeper page, review, and insert options in named menus, tabs, or panes; and direct keyboard equivalents. Word-style command breadth and Docs-style low-friction formatting are compatible when commands are grouped clearly and the document remains visually dominant.

## Keyboard and novice discoverability

- Preserve the platform's expected editing keys, then add shortcuts for high-value structural actions: heading styles, lists, links, comments, page breaks, find/replace, navigation, and focus/view controls. Keep macOS and Windows/Linux bindings distinct where conventions differ. Docs, Word, Writer, LibreOffice, and ONLYOFFICE all document broad command coverage, with Word and ONLYOFFICE additionally exposing sequential Key Tips. [Google](https://support.google.com/docs/answer/179738?hl=en) · [Microsoft](https://support.microsoft.com/en-us/accessibility/word/keyboard-shortcuts-in-word) · [ONLYOFFICE](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/keyboardshortcuts.aspx)
- Show shortcut hints in menus and tooltips; provide a searchable shortcut reference and an action search. Google exposes shortcut help; Word's `Alt+Q` searches actions; both lower the learning cost without adding permanent explanatory copy. [Google](https://support.google.com/docs/answer/179738?hl=en) · [Microsoft](https://support.microsoft.com/en-us/accessibility/word/keyboard-shortcuts-in-word)
- Use tooltips for compact icon controls, but give unfamiliar or high-consequence actions visible text. Apple explicitly advises using text when a short label is clearer than a symbol. [Apple button guidance](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Treat each toolbar as a composite keyboard widget: one Tab stop into it, arrow-key movement within it, Enter/Space activation, clear focus styling, and an accessible name. WAI-ARIA also recommends using the toolbar pattern for groups of three or more controls and documenting a direct way to move from the editor to its toolbar. [WAI-ARIA toolbar pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) · [Example](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/examples/toolbar/)
- Keep visible focus crisp against black and white surfaces. WCAG AA requires at least 4.5:1 contrast for normal text and 3:1 for large text; WCAG 2.2's enhanced focus appearance criterion describes a 2 CSS-pixel perimeter with 3:1 state contrast. [Contrast guidance](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum) · [Focus Appearance](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)

## Visual direction for this editor

The user specified a pure black / pure white foundation, restrained solid colors, minimal copy, and named controls rather than icon-only guessing. Apply that consistently:

- Make the page or canvas the main visual mass. Use solid `#fff` document paper and `#000` dark-mode chrome/canvas foundations; build separation with crisp boundaries, spacing, and a small number of neutral steps only where required for legibility. Reserve saturated color for selection, active state, comments, and meaningful status.
- Use one clear toolbar with labeled groups for text, paragraph structure, insert, and review. Keep common actions visible; put rare page-engine controls in named menus or a contextual pane. Avoid a stack of decorative cards, soft gradients, layered translucent fills, and redundant rounded containers. Apple's HIG says to choose toolbar items deliberately and avoid overcrowding; Material's color guidance recommends using colored text selectively and checking contrast. [Apple toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars) · [Material color](https://m1.material.io/style/color.html)
- Keep labels short and literal: “Heading 1,” “Insert table,” “Page layout,” “Comments.” Use familiar icons beside labels where space permits; icon-only controls need an accessible name and, for uncertain meanings, a visible-on-hover/focus text hint. Apple advises a short text label whenever it communicates more clearly than a symbol. [Apple buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)
- Make command groups, active states, and selection states distinguishable by shape/border/position as well as hue. Keep color as emphasis, not decoration. Use stable typography and spacing instead of extra copy to teach hierarchy. Apple's help guidance says that if a control needs a lot of text to explain it, simplify its design. [Apple offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help) · [Material color](https://m1.material.io/style/color.html)
- Put contextual controls close to the current selection or page object; keep global document actions in a stable location. Keep document settings, review, and navigation surfaces task-specific and closeable, so people can recover the writing canvas quickly. These placements align with the selection-based Docs/Pages/Word formatting model and Craft's separation of text styling from page styling. [Docs](https://support.google.com/docs/answer/1663349?hl=en) · [Craft](https://support.craft.do/hc/en-us/articles/10293992410780-Document-Styling)

“Non-AI-slop” is not a formal product-design standard. For this project, treat it as a testable set of craft constraints: every visible control maps to a real editing job; every color signals hierarchy or state; no decorative cards or copy repeat what an icon, label, or document structure already makes clear; and each shortcut/search path produces the same result as its visible command. These constraints follow the first-party toolbar, color, and accessibility guidance cited above rather than relying on aesthetic trend claims.

## Design decisions to carry into implementation

1. Start from the actual editing workflow and the current engine capabilities; do not copy a ribbon, block editor, or inherited component kit wholesale.
2. Use a familiar word-processor frame: title/document actions, compact labeled formatting toolbar, central page canvas, optional navigation/review pane, and a compact status/zoom area.
3. Add command search and shortcut discovery early. Keep formatting labels visible for first-time users; use icons as reinforcement.
4. Use progressive disclosure for advanced layout and engine actions. Do not hide common format, insert, or review controls behind a generic overflow menu.
5. Design light and dark modes as deliberate black/white systems with solid fills, strong text contrast, legible borders, and an unmistakable focus indicator.
6. Verify with representative tasks: style a heading, create and navigate a table, insert a page break, find/replace, review a comment, switch page setup, and perform each by keyboard alone.

## Word ribbon follow-up

The follow-up uses Word's simplified ribbon as the specific layout reference. Microsoft describes a single command row, related commands under dropdowns, and width-dependent overflow into More options. Its reference page includes classic/simplified comparison images. This editor adopts inline icon/label controls, smaller row heights, and responsive whole-group overflow while preserving existing formatting fields, menus, and contextual tools. [Microsoft's single-line ribbon reference](https://support.microsoft.com/en-us/word/using-the-simplified-ribbon-in-word-for-the-web)
